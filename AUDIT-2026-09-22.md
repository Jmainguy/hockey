# Hockey site audit — September 22, 2026

Scope: live desktop and 390px mobile browser checks, read-only Kubernetes/Redis inspection, and source review. No application or production changes were made. Production runs `zot.soh.re/jmainguy/hockey:v1.13.0`; local HEAD is `fbeb6aa` (`v1.12.0-3-gfbeb6aa`). Source findings below refer to this checkout; verify the release diff before implementation.

## Observed in production

- Home remained at “Loading teams…” across the inspection. The mobile Select Team button did nothing when clicked during this state.
- Standings remained at “Loading standings…”.
- `/scores` successfully displayed September 22 preseason fixtures.
- `/team/car` displayed roster statistics while its header remained “Loading team data…”. The roster did not identify the season associated with the displayed statistics.
- Both application and Redis pods were Running, ready, and had zero restarts. Application deployment has one replica, no configured readiness/liveness probes, and no resource requests or limits.
- Logs around 11:19 UTC showed successive empty historical standings responses, followed by actual upstream 429s and 30-second retry sleeps. This is confirmed rate limiting, not merely a frontend error label.
- Redis held all 32 current-season roster keys. `TTL roster:CAR-20262027` returned `-1` (no expiration).

## Prioritized findings

### P1 — Standings discovery amplifies upstream requests and blocks navigation

`nhl_api.go:1006–1053`: lookup tries 62 dates, starting with 46 consecutive days. Empty standings are not cached, so subsequent visitors repeat the scan even when an older successful date is cached. `GetAllTeams` depends on this path, tying a basic team directory to volatile standings availability. Live logs reproduce this scan and subsequent 429s.

Fix: serve a stable team catalog independently; retain one last-successful standings snapshot with its season/date; refresh in the background; briefly cache valid empty responses; bound discovery and stop on upstream throttling.

### P1 — Retry delays occur inside user requests

`nhl_api.go:394–510`: one failing resource can sleep for 30 + 60 + 120 + 300 seconds (8.5 minutes), excluding network time and lock waiting. The outer standings loop can then continue to another date. Sleeps and upstream requests do not honor the browser request context. No stale snapshot is retained by this helper after TTL expiry.

Fix: short request deadlines, serve last-known-good data with freshness metadata, and background retries honoring Retry-After with a shared cooldown.

### P1 — Schedule polling bypasses successful cache entries

`main.go:433`: the schedule handler fetches upstream first and consults Redis only after a 429. It stores successful responses but does not use them on the normal path. `static/scores.js` starts a 10-second polling interval, including when the day's games are not live.

Fix: cache-first schedule service, appropriate live/upcoming/historical TTLs, and polling only when needed, paused for hidden tabs.

### P1 — Each game landing request fetches upstream twice

`main.go:484` calls `GetGameLanding` (an uncached fetch at `nhl_api.go:831`), then unconditionally fetches the same URL again for raw JSON. Live score cards request these endpoints too. A successful first fetch can be discarded when the second is throttled.

Fix: fetch/cache one raw payload and derive typed and enriched representations from it.

### P1 — Request deduplication fails under slow/throttled fetches

`nhl_api.go:409–433`: waiters proceed without a lock after 30 seconds. Locks expire after two minutes although retries can last 8.5 minutes. Lock deletion is unconditional and does not verify ownership, allowing an old worker to delete a newer worker's lock. The warmer also wraps resource functions in the same cache helper; paths such as schedule/player/roster can attempt to acquire their own already-held key.

Fix: one owner per resource fetch, process-level singleflight, ownership-safe distributed locks if needed, and no synchronous duplicate fetch after the wait budget expires.

### P2 — Live-game detection uses the wrong schedule schema

`nhl_api.go:730`: checks `dates`, while the schedule payload used by the frontend contains `gameWeek`. Consequently a valid schedule can parse without error but contain no games in this structure, choosing non-live TTLs. Also, schedule readers share a key written with either a one-minute or one-hour TTL.

Fix: one typed schedule schema and a single cache policy; test with a fixture containing a LIVE game.

### P2 — Permanent roster caching freezes changing data

`nhl_api.go:721`: roster/static TTL is zero. Production confirms a roster without expiration. Rosters change during a season, and cached processed rosters may include statistics that age independently. Cold roster enrichment also fetches players serially and can sleep 3.5 minutes per throttled player (`nhl_api.go:1847`).

Fix: finite roster TTL, separate roster membership from player statistics, asynchronous/bounded enrichment, and season/freshness labels.

### P2 — Loading and failure states leave visitors stranded

`static/app.js:129`: non-OK team responses retain loading UI and schedule indefinite retries; fetch has no explicit timeout. Mobile picker handlers are installed only after teams load. Standings exposes technical HTTP errors after failure, with no useful recovery action. Live team content partially loads without explaining the missing header.

Fix: render navigation immediately, show cached content or a clear temporary-unavailable state, provide retry controls, and preserve usable sections independently.

### P2 — Keyboard access is missing for clickable cards

`static/scores.js:createGameCard` creates clickable `div` elements with mouse handlers, rather than links. Browser accessibility inspection identifies them as containers, not links. Roster cards similarly appear as containers.

Fix: semantic links/buttons with visible keyboard focus; dialogs need explicit accessible names, focus management, and Escape handling.

### P2 — Additional transport and operational weaknesses

- `rateLimitedGet` uses `http.Get` without an explicit timeout (`nhl_api.go:2224`), unlike the other HTTP client.
- Rate limiting is process-local; adding replicas multiplies the upstream budget.
- No readiness/liveness probes or resource requests/limits in the running app deployment. Ready status therefore does not establish that data endpoints work.
- Templates rely on externally loaded Tailwind runtime for utility styling (`templates/index.html:9`). Compile and serve CSS locally to remove a runtime dependency.

## Design recommendations

These are visual judgments, separate from confirmed functional bugs.

- Replace large blue gradients, emoji headings, glass effects, heavy shadows, and oversized rounded panels with a restrained navy/charcoal, off-white, and single-accent palette.
- Use one consistent sans-serif family, fewer extra-bold weights, and tabular numerals for scores/statistics. The current visual problem is hierarchy and decoration as much as font selection.
- Reduce header height. At 390px the header occupies roughly 280px before useful content; during failure nearly the entire screen becomes header plus empty space.
- Use compact scoreboard rows. At the inspected desktop size, roughly two complete fixtures fit vertically despite ample horizontal space.
- Keep team colors mainly in logos and small accents; use consistent navigation, spacing, and table treatments across pages.
- Label preseason/regular-season/playoff context, statistics season, and last-updated time. Historical fallback data must not silently appear as current standings.

## Suggested implementation order and acceptance checks

1. Unify upstream fetching/caching, eliminate duplicate requests, decouple teams from standings, and introduce stale-data fallback and cooldowns.
2. Add focused tests with simulated 429s, empty standings, concurrent requests, cache expiry, and live-game schedule fixtures. Confirm repeated visitors do not multiply upstream calls and canceled requests stop work.
3. Fix loading/retry states, semantic navigation, and season/freshness labeling.
4. Apply a shared visual system to home, scores, standings, and team/player pages; verify desktop and mobile behavior.
5. Reconcile local source with deployed v1.13.0, release through the existing deployment workflow, then verify logs, request counts, and browser behavior.

No live game was in progress during inspection, so live-clock behavior is a source-level finding rather than a reproduced live-game failure. No load test was run against the already-throttled service.
